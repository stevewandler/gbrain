Get it running

Clone and go

Mockups — future direction

Pure frontend. Nothing to configure, no keys, no database.

# one time
gh repo clone BookmarkED-Corp/bookmarked-onshelf-mockups
cd bookmarked-onshelf-mockups
npm install

# every time
npm run dev   → localhost:5173

Demo — if you ever need it locally

Needs a Supabase key in .env.local to write. Reads work without one.

# one time
gh repo clone BookmarkED-Corp/bookmarked-bi-replica
cd bookmarked-bi-replica
git checkout demo && npm install

# every time
npm run build && npm run local
→ localhost:3100

The demo serves its frontend from the built dist/ folder, so a change to src/ needs npm run build before you'll see it. The mockups repo hot-reloads normally.

Reference — Patrick's loop

Spec to handoff, every time

Step 1 is the one people skip and the one that causes the most pain later.

Re-sync from production before touching anything

If your copy has drifted, your change won't apply cleanly when Engineering gets it — and you won't find out until the end. Never start a ticket on last month's copy.

Read the spec, then branch named after the ticket

One spec, one branch, one pull request — spec/V2KAN-412-flag-source-labels. The ticket number is what lets anyone trace a change back to the customer who asked for it.

Make the change in src/ only

Everything under src/ is the real product interface. Anything outside it is local scaffolding that makes the app runnable on your laptop — it must never appear in your diff.

Run it and look at it

Click the actual screen and confirm it does what the spec asked. Reading the code back is not verification. Screenshot before and after.

Open the pull request with the spec linked

Body carries: what the customer asked for, what changed, before/after screenshots, and anything you chose not to do.

Engineering applies it — not you

Nobody here pushes to the production repo. That boundary is why a designer can work on the interface without ever holding access to the backend, infrastructure, or secrets.

Reference — working in parallel

The rules that prevent collisions

Different repos, so conflicts can't happen

Steve in mockups, Patrick in the UI repo. Two people editing the same file at the same time is structurally impossible — the real answer to "how do we both work at once."

The Jira ticket is the claim

Assigned to you means the screen is yours until the pull request closes. Want a screen someone else has? Say so in the ticket rather than opening a second branch on it.

Worth knowing

Claude Design is for looking, not shipping

Good for exploring a visual idea fast, but it can't reach these repos and can't post to Confluence. Treat its output as a reference image, never the deliverable — the real change gets made in Claude Code afterwards.

Hard line

Nobody gets access to the production repo

The live interface sits in a monorepo alongside every backend service, the infrastructure config, access policies and secrets. GitHub grants access per repository, not per folder — so there's no "just the UI folder." That's why these separate repos exist.

Reference — background

Why this needed writing down

The two existing repos both break what Patrick needs

The demo repo says so in its own README: "Never push changes from here back toward Bookmarkedv2. This copy diverges on purpose." The mockups repo builds brand-new screens in isolation, not the live app.

Patrick's work needs the opposite of both — a copy that tracks production faithfully, so a change still applies cleanly when Engineering picks it up. Hence a third repo, with the opposite contract.

One practical note: the live interface expects five backend services running on your machine before it will load a page. That's why Patrick's repo will ship with a lightweight local stand-in — nobody should need Docker to change a label.
